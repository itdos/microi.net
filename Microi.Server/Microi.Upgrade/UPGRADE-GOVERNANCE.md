# Microi.Upgrade 治理与审计基线

最后审计：2026-09-04

## 结论

`Microi.Upgrade` 不是业务应用资源的发布渠道。表、字段、菜单、页面、工作流、接口引擎、微服务和可幂等种子数据默认进入对应官方应用包；升级程序集只保留应用商城尚不能表达、且新运行时在打开商城前必须具备的物理兼容、存储或协议迁移。

本次检查覆盖 `01` 至 `35` 共 33 个历史升级文件及启动门禁、后台租户协调器和版本推进逻辑。历史文件暂不物理删除：旧库可能从任意版本直接升级，后续步骤也可能依赖它们已经创建的物理结构。它们进入“冻结兼容链”，只允许修复幂等、跨库、事务和安全缺陷，不再追加新的业务应用资源。

## 发现与处理

| 范围 | 审计判断 | 处理 |
| --- | --- | --- |
| `01`–`12` | 早期空库和核心表物理兼容，旧版本跨级升级仍依赖 | 保留并冻结 |
| `13-UpgradeAppStore` | 应用商城导入器、内置基础包和启动闭包的引导层；商城无法在自身不可用前替代它 | 保留，但新资源必须先归属官方基础包 |
| `14`–`35` | 混合了历史物理迁移与今天可由商城表达的元数据；删除会破坏旧库直接升级和步骤依赖 | 保留为历史一次性链，不再按启动不变量重复执行 |
| AI 工作流蓝图三表 | 独立平台应用的声明式资源，商城能够完整交付 | 仅进入 `app.microi.ai-workflow`，禁止新增 .NET 升级点 |
| 启动时 13 组子租户不变量 | 协调器与版本链重复执行，租户数越多启动成本越高 | 由 `Upgrade36` 一次性封口，完成后走版本快路径 |

旧协调器对每个已加载子租户先执行物理门禁、取得分布式租约、重放 13 组不变量，再读取 `ServerVersion`；`Upgrade()` 内又重复了其中一部分。即使租户已经是最新版，成本仍近似 `租户数 × 历史不变量数`。

现在的顺序是：

1. 读取该租户 `sys_config.ServerVersion`。
2. 已达到目标基线时立即返回，不取分布式租约、不跑历史迁移、不刷新缓存。
3. 仅落后租户检查启动物理前置条件并取得共享租约。
4. 在租约内再次读取版本；若另一节点已经完成则立即返回。
5. 执行尚未覆盖的版本链；`Upgrade36` 对以前每次启动重放的兼容项做最后一次幂等封口。
6. 所有步骤成功后才以前向 CAS 推进 `ServerVersion`；任一步失败都不推进，重试仍从可验证状态开始。

主租户在 API 接收流量前仍保留最小物理字段和商城启动闭包门禁。这只作用于当前部署主租户，不会串行门禁数百个子租户；后台子租户扫描在当前版本下只产生一次版本读取。

## 新升级点准入门禁

新增 `Microi.Upgrade` 文件前必须在评审中同时回答：

1. 为什么应用商城的 `DiyTables`、`DiyFields`、`DDLStatements`、`PhysicalColumns`、`DataSets`、菜单、引擎或应用包依赖无法表达？
2. 该能力是否在应用商城/登录恢复入口可用之前就必须存在？
3. 它依赖哪些更早升级点；从空版本和任一历史版本进入是否都不会跳过依赖？
4. 是否使用新的四段版本、共享租约、可重入实现和强回读？失败时是否明确不推进版本？
5. 已是当前版本的数百租户是否只做常数次轻量读取，而不是再次扫描历史表/字段/索引？
6. MySQL、SQL Server、Oracle 和至少两个节点并发执行是否有证据？

任何一项不能成立，默认改为官方应用包升级。不得把某个客户租户缺表的事故修复写成所有租户永久承担的启动迁移。

## 依赖与版本规则

- 历史链即使有部分资源今天可以由商城表达，也不能直接删除；必须先证明所有仍受支持的起始版本都不依赖它。
- 新步骤使用高于当前目标的唯一四段版本，并追加在执行链末尾。不得通过抬高旧步骤版本制造非单调顺序。
- 一个高版本基线可以封口旧版“版本已推进但结构可能漂移”的历史问题；封口完成后，后续修复必须新开版本或发布应用包，不能恢复为每次启动全量复检。
- 若步骤 B 依赖步骤 A，A 必须继续位于同一版本链的前面，或把 A 的必要物理前置条件并入 B 的幂等检查；不得仅因 A 可迁移到商城就让历史直升路径断裂。
- 包级资源需要单调应用版本、不可变 HDFS 指针、SHA-256、安装任务终态和目标租户强回读；`ServerVersion` 不能代替应用安装版本。
